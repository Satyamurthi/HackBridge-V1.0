HackBridge — PRD & Build Prompt

Oct 26, 2026 · @Satyu

1. Product overview

HackBridge is a web platform where colleges and companies host hackathons and students apply, pay, compete, submit and keep their work, all in one place. The target is a production-ready v1 with four roles, automated team and payment flows, fair problem-statement allocation and judge scoring.

Problem. Hackathon organizers juggle forms, payment screenshots, spreadsheets and chat groups. Students have no single identity, no proof of past participation and no place to keep their code.

Goals

Let a host publish and run a full hackathon from one dashboard, end to end.

Give every student one permanent Hackathon ID and one-click team formation.

Verify payments automatically (Razorpay) or manually (QR) before issuing a Team ID.

Allocate problem statements fairly: equal teams per statement, first come first served.

Store every team's code in GitHub, named by Team ID, viewable and downloadable later.

Give the super admin universal control over hosts, content and site layout.

3. Functional requirements

Each module lists what must work for release. IDs (FR-x) are for tracking.

FR-1 Authentication and identity

Email plus password signup with email verification, plus Google login for students.

On student signup the system generates a unique, permanent Hackathon ID (format HB-XXXXXX), shown with copy and share buttons.

Separate signup flows for student, host and judge. Host signup lands on a pending-approval screen. Judge signup requires a hackathon ID, otherwise the request is rejected.

Password reset, session management, rate-limited login.

FR-2 Hackathon listing and discovery

Public list with search and filters (host, date, mode, fee, domain) and a live countdown on each card.

Detail page: banner, host, rules, prize pool, schedule, domains with their own countdown timers, fee, deadline.

FR-3 Host hackathon builder

Multi-step wizard: basics, rules, domains with exact start date and time, problem statements (hidden until the timer ends), team size limits, fee, payment method, judging rubric, GitHub credentials, publish.

Rules gate toggle: either show rules and require agreement before applying, or send students straight to apply.

Publish is blocked until the host is approved by the super admin.

FR-4 Team formation and application

Only the team lead can open the apply form. The lead enters teammate Hackathon IDs; each is validated live (exists, not already in another hackathon, not already in this team).

Duplicate application by any member is rejected with a clear message.

After teammates are added the lead goes directly to payment.

FR-5 Payments

Razorpay mode: host stores credentials (encrypted); checkout, webhook verification, then Team ID auto-generated.

QR mode: host uploads QR; team submits transaction ID and screenshot; host approves or rejects; Team ID is generated only on approval.

Payment status visible to team and host: pending, verified, rejected, refunded.

FR-6 Problem-statement allocation

Statements stay hidden until the host-set timer reaches zero, then unlock together in real time.

Per-statement cap = ceil(registered teams / number of statements). Selection is first come first served; a full statement locks instantly for everyone.

Selection must be atomic (no two teams can take the last slot) and final.

FR-7 Live hackathon workspace

Progress scale from 10% to 100% in 10% steps; teams are prompted to update every 30 minutes and every update is timestamped in a timeline.

Judges and the host see all teams' progress live. Teams cannot see other teams' progress or results.

Code storage: upload files or a zip; each team's code is pushed automatically to a new GitHub repository named after the Team ID, using the credentials the admin configured.

FR-8 Submission

One-time final submission: project link, or uploaded application or .exe file, plus a required description of how it works.

Confirmation dialog states that submission cannot be changed. After submission the form and uploads are locked.

Uploaded files are virus-scanned and size-limited.

FR-9 Judging

Host defines rubric criteria and weights; any number of judges per hackathon, each approved by the host.

Judges open each team's submission and stored code, enter scores per criterion and notes. Weighted totals and ranking are computed automatically.

Scores are visible only to the host, super admin and the judge who entered them. Teams see only their own final result.

FR-10 Results and history

Host publishes winners. Students get a hackathon history page: events attended, team members, award and prize, stored code with view and download.

FR-11 Super admin panel

Approve, add, delete and pause hosts and judges; moderate or remove any hackathon; view all users.

Site CMS: edit landing page sections, text, banners, navigation, footer, columns and theme, with preview and publish.

Global settings: GitHub organisation and token, payment and email settings.

Platform analytics and audit log of all admin actions.

FR-12 Notifications

Email and in-app notifications for approvals, payment status, timer start, 30-minute progress reminders, submission confirmation and results.

4. Business rules and edge cases

Rule

Behaviour

Edge case handling

One student, one hackathon

A Hackathon ID can belong to only one active registration at a time

Enforced by a database unique constraint, not only UI checks; lead sees which teammate is blocked

Team lead owns applying

Only the lead applies and adds members

Teammates see an "added to team" notice; lead cannot add themselves twice

Team ID after payment only

Razorpay: after verified webhook. QR: after host approval

If payment fails or is rejected, members are released and can apply again

Slot balancing

Cap per statement = ceil(teams / statements)

Recalculate cap if the host changes team count before the timer; lock after unlock

First come first served

Atomic transaction with row lock on the statement

Two simultaneous picks: one wins, the other gets "slot just filled, choose another"

Timer-based reveal

Server time is the only clock

Client countdown syncs from server; early requests for statements return nothing

Progress updates

Every 30 minutes, 10% steps, never decreasing

Missed update is flagged to judges, not blocked

Final submission

One submission per team, locked after confirm

Only the host can unlock a submission, and the action is logged

Judge approval

Judge must provide a valid hackathon ID; host approves

Wrong ID rejects the request; judge access ends when the hackathon is archived

Result privacy

Teams see only their own result

API enforces this server-side, not by hiding UI

Paused or deleted host

Paused: no new registrations, existing event continues read-only. Deleted: soft delete, data retained 90 days

Active hackathons of a deleted host require admin reassignment or refund flow

Code storage

Repo named by Team ID, created automatically

Repo creation failure retries three times, then alerts admin and keeps the files in object storage

Key flows

Apply: lead submits team IDs, server validates in one transaction, creates a pending team, then payment starts.

Razorpay: order created server-side, checkout on client, webhook verifies signature, team becomes active, Team ID generated.

QR: team uploads proof, host approves, team becomes active, Team ID generated.

Statement selection: client calls select, server locks the statement row, checks the cap, assigns, then broadcasts the new slot count.

Code push: files land in storage, worker creates the repo named by Team ID and pushes a commit.

7. Non-functional requirements

Area

Requirement

Security

Role-based access checked on the server for every endpoint; passwords hashed with Argon2 or bcrypt; secrets encrypted at rest; CSRF and XSS protection; rate limits on login, ID lookup and statement selection; signed Razorpay webhooks only

Data privacy

Collect minimum student data; consent at signup; export and delete on request; follow India's DPDP Act requirements

File safety

Virus scan on uploads including .exe; size limits; files served from a separate domain; never executed on the server

Performance

p95 API under 300 ms; pages under 3 seconds on 4G; 3D scenes lazy-loaded, with a static fallback on low-end devices

Scalability

Handle 5,000 concurrent users during a problem-statement unlock; load-test this flow before launch

99.5% uptime; daily database backups with restore tested; idempotent webhooks and retries

8. Phased roadmap

Durations assume one full-stack builder working with an AI coding agent; scale them to your team.

Phase 1, Foundation (weeks 1-2): project setup, design system from Stitch, auth, roles, Hackathon ID, database schema, CI. Gate: all four roles can sign up and log in.

Phase 2, Host and listing (weeks 3-4): host approval, hackathon builder, domains and timers, public listing and detail pages, super admin host management. Gate: an approved host can publish a hackathon.

Phase 3, Apply and pay (weeks 5-6): team formation, one-hackathon rule, Razorpay and QR flows, Team ID generation. Gate: a team can register and pay end to end.

Phase 4, Event day (weeks 7-8): problem-statement reveal and balanced allocation, progress scale, code storage and GitHub push, submission lock. Gate: load test of the unlock passes.

Phase 5, Judging and history (weeks 9-10): judge signup and approval, rubrics, scoring, results, student history, admin CMS. Gate: a full mock hackathon runs without manual fixes.

Phase 6, Hardening and launch (weeks 11-12): security review, accessibility, performance, backups, legal pages, monitoring, pilot with one college. Gate: pilot hackathon completes and feedback is addressed.
